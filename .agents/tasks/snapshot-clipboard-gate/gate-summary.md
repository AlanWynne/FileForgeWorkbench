# Gate Summary -- snapshot-clipboard-gate (CR-CH-079)

Requirements gate (docs only, NO `.rs` changed, no cargo gate run) for the
owner-confirmed requirement that each snapshot clipboard TEXT flavor must carry
BOTH the box-drawn layout AND the property/value pairs as tables.

## New criteria ids

`screen-snapshot-scrm` Requirement 28 (CR-CH-079), criteria 28.1 - 28.8:

- 28.1 Plain-text (`CF_UNICODETEXT`) flavor contains box-drawn layout AND
  property/value Markdown tables.
- 28.2 Composite rich (`CF_HTML`) flavor contains PNG image AND box-drawn layout
  AND property/value HTML tables.
- 28.3 PNG picture flavor UNCHANGED.
- 28.4 Ordering: box-drawn layout FIRST, then tables (in CF_HTML: image, then
  box, then tables).
- 28.5 CF_HTML retains the Req 23.5f monospace per-line `<span>` treatment; byte
  offsets stay correct after the markup grows.
- 28.6 Tables in both flavors derive from the SAME logical content (the Markdown
  renderer's `markdown_sections` / `fields` / `tables`), so both show identical
  data and grouping, differing only in table syntax.
- 28.7 GENERAL rule for all table-bearing snapshots (shared renderer path), not
  Config-specific; box-only and tables-only Contexts are unaffected.
- 28.8 Existing single-format outputs (`SNAPSHOT MARKDOWN`/`HTML`/`TEXT`, file /
  PDF export) are preserved / reconciled.

## Flavor-structure investigation verdict (settled against the code)

Read: `crates/ff-screen-model/src/render/{text,markdown,html}.rs`,
`crates/ff-screen-model/src/model.rs`,
`crates/ff-desktop/src/shell/screen_providers_config.rs`,
`crates/ff-desktop/src/shell/commands_snapshot.rs`,
`crates/ff-desktop/src/clipboard_html.rs`.

- The SNAPSHOT places THREE OS clipboard flavors in one transaction (Req 23):
  `CF_DIB`/`CF_DIBV5` (the real window PNG), `CF_UNICODETEXT` (plain text), and
  `CF_HTML` (composite rich). The flavor COUNT is not changing.
- WHICH flavor omits WHICH today, and WHERE each representation is generated:
  - `CF_UNICODETEXT` (Notepad) = `render_snapshot(model, Markdown)`
    (`render/markdown.rs::render_markdown`). For a Context that populates
    `model.markdown_sections` (the Config panel does, via
    `config_capture_markdown_sections` in `screen_providers_config.rs`),
    `render_markdown` takes the `markdown_sections` branch and RETURNS EARLY --
    emitting the per-group `Property | Value` tables ONLY and NEVER the fenced
    box-drawn body. => Notepad currently gets TABLES, MISSING the box. (Matches
    the owner's observation.)
  - `CF_HTML` (Word) = `clipboard_html::build_cf_html(png, pre_text)`, where
    `pre_text = render(model, PlainText, default)` -- the box-drawn body from
    `render/text.rs::render_plain` (which renders `body_lines` verbatim inside
    the frame). `build_cf_html` emits the PNG `<img>` paragraph + one monospace
    `<span>` paragraph per box line and renders NO tables at all. => Word
    currently gets IMAGE + BOX, MISSING the tables. (Matches the owner's
    observation.)
  - Root cause: the two text flavors use DIFFERENT renderers, and for a
    `markdown_sections` Context the Markdown renderer swaps the box body OUT for
    tables while the CF_HTML path only ever carries the box body.
- Box-drawn layout is generated by `render/text.rs` (plain + the CF_HTML
  `<pre>`-equivalent per-line spans). Property/value tables are generated by
  `render/markdown.rs` from `model.markdown_sections` (Config) or
  `model.fields` / `model.tables` (generic). The HTML renderer
  (`render/html.rs`) can render `fields` / `tables` as `<table>` today but is
  NOT on the clipboard composite path and does NOT render `markdown_sections`.

## Chosen ordering

Box-drawn layout FIRST, then the property/value tables, in BOTH flavors. In
`CF_HTML`: the PNG image paragraph first (as today, Req 23.5f), then the
box-drawn monospace body, then the HTML tables. This mirrors the visual reading
order (framed screen, then its data broken out as tables) and preserves the
existing image-then-box ordering of the composite. It also matches the generic
Markdown path, which already emits the fenced body before the property table and
table elements.

## General vs Config-specific decision

GENERAL. Implemented in the shared `ff-screen-model` renderers
(`render_markdown` box-then-tables; a new `render/html.rs` table emitter) and the
shared `clipboard_html` composite (`build_cf_html` gains a `tables_html`
parameter), so every Context whose model carries both a box layout and tabular
content inherits the behaviour. A box-only Context (no tables) and a tables-only
Context are unaffected. This follows the reusability principle in
`framework-conformance.md`.

## Framework check

Builds ON the existing SCRM clipboard flavors (Req 23) and the `ff-screen-model`
renderer / `Table` / `MarkdownSection` model. NO new clipboard flavor, NO new
framework mechanism, NO change to `resolve_target` / dispatch, NO reshape of a
public `ff-screen-model` / `ff-scrm` type (`ScreenModel`, `ScreenProvider`
untouched). => No framework change; no owner framework confirmation required
beyond approving this gate.
