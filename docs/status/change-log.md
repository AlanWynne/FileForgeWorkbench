### CR-NR-087 -- Bare UP/DOWN (PF7/PF8) honour the active SCROLL amount (PAGE/HALF/MAX/CSR/DATA/n) [B046]
- **Date/Phase**: Phase (bug-sweep) (gate, Wave 4a) -- PENDING GATE (owner scheduling)
- **Prompt**: (from B046, owner) "Up Max and Down Max should not be bound ... they should be up and down only and only Down Max When we type m or max on the command line and press the up or down key". The ISPF model is that the `SCROLL ===>` field amount governs PF7/PF8: with `SCROLL MAX` active, UP/DOWN scroll to top/bottom; with `SCROLL HALF`, half a page; etc.
- **Description**: Today bare `UP`/`DOWN` always scroll exactly one page (`nav_manager.up`/`.down` call `up_page`/`down_page` and never consult `self.scroll_amount`), which is spec-compliant with navigation-commands Req 3.1/3.3 as currently written but does NOT implement the ISPF `SCROLL`-amount-governed behaviour the owner described for B046. Proposed: when `UP`/`DOWN` is issued with NO explicit numeric argument, scroll by the currently active `ScrollAmount` -- PAGE (one page, current default), HALF (half a page), MAX (to top/bottom), CSR (cursor-relative), DATA (data-relative), or n (n lines). An explicit `UP n`/`DOWN n` still overrides with a line count (Req 3.2/3.4 unchanged). This is why row 7.3a currently fails: MAX-then-UP does not scroll to top.
- **Status**: PENDING GATE
- **Linked spec**: `docs/specs/navigation-commands/requirements.md` Requirement 3 (criteria 3.1/3.3 revised + new 3.17 for SCROLL-amount-governed UP/DOWN); relates to `ff-desktop` `scroll_amount.rs` (`ScrollAmount`), `nav_manager.rs`, menu-and-statusbar Req 19 (SCROLL field). Completes a B046 remnant (the MAX modifier); does NOT re-bind PF7/PF8 (they stay UP/DOWN).

### CR-NR-085 -- Save-durability failures must surface (never silently swallowed) [B034]
- **Date/Phase**: Phase (bug-sweep) (gate, Wave 1)
- **Prompt**: (bug B034, prioritised in the outstanding-bug sweep) "Durability failures in the save path are silently swallowed ... discard the results of flush().await, sync_all().await, close().await ... a non-durable save can fail silently."
- **Description**: B034 is a bug against existing file-operations Req 7.1/7.2 ("flush and fsync the temporary file") and 7.5 (backup-fail logs WARN), but it also reveals a MISSING criterion: the requirement says fsync happens but never says what must happen when flush/fsync/close FAIL. Today `AtomicWriteStrategy`/`DeleteFirstStrategy`/`DirectWriteStrategy` discard those results with `let _ = file.flush()/.sync_all()/.close()`, and the "can't open for fsync" arm silently continues -- so a save can report success while the data was never durably flushed (data-integrity risk). `save.rs` also drops a failed backup with `let _ = e` and a comment "In production this would use ff-logging WARN" -- violating existing 7.5. This CR adds the durability-failure criteria (fsync/flush failure aborts the Atomic save with an error and logs it; the fsync-open failure is not silently ignored; the direct/delete-first strategies surface their fsync failures) and fixes the backup-fail to actually log WARN per 7.5.
- **Owner decisions (assumed, confirm)**: for the ATOMIC strategy a flush/fsync failure on the temp file is FATAL (abort before the rename, so a half-written temp never overwrites the good target); for a provider that cannot be re-opened for fsync, the save proceeds but logs a WARN (reduced crash-safety, mirroring 7.2) rather than silently continuing; for direct/delete-first (already non-atomic) a fsync failure logs a WARN (best-effort durability) and does not falsely report a clean save.
- **Affects**: `crates/ff-file-ops/src/persistence.rs` (check flush/sync_all/close results in all three strategies; the atomic path aborts+cleans-up temp on fsync failure), `crates/ff-file-ops/src/save.rs` (backup-fail logs WARN via ff-logging, per 7.5). `docs/specs/file-operations/requirements.md` Req 7 (add criteria 7.10-7.12). Docs: design.md delta, tasks.md; project-master; TCR; core acceptance test-plan Group 4/new durability row.
- **Status**: DONE
- **Implemented**: `persistence.rs` -- AtomicWriteStrategy checks `flush()`/`sync_all()` of the temp file and, on failure, deletes the temp, `log_error!`s, and returns `FileOpsError::VfsWriteError { operation: atomic_write_flush|atomic_write_fsync }` BEFORE the rename (non-durable temp never overwrites the target); the re-open-for-fsync failure `log_warn!`s (reduced crash-safety) instead of silently continuing; a post-fsync `close()` failure `log_warn!`s. DirectWriteStrategy/DeleteFirstStrategy `log_warn!` on flush/sync_all/close failure (best-effort, Req 7.11). `save.rs` backup-failure `let _ = e` replaced with `ff_logging::log_warn!` (Req 7.5/7.12), save still proceeds. Tests: 5 new in `persistence_tests.rs` (atomic abort on fsync/flush failure -- confirmed RED first; happy path; direct/delete-first best-effort) via a `FailOn::Flush`/`Fsync` mock injection; the non-fatal-path WARN emission is MANUAL (needs a running log subsystem). verify.ps1 CLEAN (FULL, nextest). Fixes B034.
- **Linked spec**: `docs/specs/file-operations/requirements.md` Requirement 7 (Atomic Write and Backup, criteria 7.10-7.12 added); logging-subsystem Req 7 (multi-crate log coverage). Fixes B034.
